- **2026-10-05 — Slice-doc conventions for the deep pass** (model.lead; technical shapes, no
  domain content). Every doc follows these and states each rule in its own words where it bites
  (a slice doc is a self-contained spec); this entry keeps the docs consistent. Proposed to Mike
  Key as a constitution amendment (brief 10, A5).
  - **Ids:** ToolId, NeighborId, LoanId, HoldId are UUIDs chosen by the caller of the command
    that creates the thing (retry-safe). A missing or malformed id is bad input, not an
    invariant refusal.
  - **Idempotency:** repeating a create command with the same id and the same details (compared
    after trimming) succeeds and records nothing new, whatever has happened to the thing since;
    the same id with different details is refused.
  - **Who is asking:** every neighbor command carries `neighborId` for the acting neighbor. Two
    refusal conditions, two names used everywhere: `requester-mismatch` (the request isn't from
    the neighbor it names — how that's known is brief 10 A1) and `not-your-loan` /
    `not-your-hold` (the loan or hold named isn't that neighbor's). Checked first, before the
    repeat check.
  - **Reads are guarded like commands:** a view a role may read refuses any other caller —
    `not-shed-manager` for the shed-manager views, `requester-mismatch` when a neighbor asks for
    another neighbor's account, loans or holds, and `not-signed-in` for any caller with no
    sign-in (every command and view except Sign Up). Each guarded view states it as an
    invariant with a scenario. (Consequence of A1 / Amendment 6; the read side goes into
    Amendment 6's wording — added with Mike Key's "ok", 2026-10-05.)
  - **Email capitals:** uniqueness always ignores case (B4). A sign-up repeat (same neighbor id)
    compares the email ignoring case; Change Email treats a change of capitals only as a real
    change — it's the only way to correct how an address is written.
  - **Sorting by name** compares names ignoring case; ties keep the creation-time order (A4).
  - **Lengths** count user-visible characters (not bytes), after trimming.
  - **Repeats of other commands:** a command that changes something that already exists
    (extend, return, cancel, suspend, reinstate, retire, record lost, close, change email) is
    safe to repeat: a request whose effect has already happened, from the same person, succeeds
    and records nothing. Only a request that would do something different is refused.
    Commands that set a state (change email, suspend, reinstate) carry no "from" value: a late
    copy of an older request is treated as a new request, accepted because retries follow
    within seconds and the change can be undone. Commands that add (Extend Loan) carry a "from"
    value so a repeat can't add twice.
  - **Times and dates:** event times are UTC instants set by the system when the event is
    recorded (`…At`, marked `assigned` in the .em). Every day rule (due, overdue, collect-by,
    90-day window) uses calendar dates in the shed's local time zone. A loan's due date is
    `dueDate` on every event that sets it (Tool Checked Out, Loan Extended); a set-aside's
    collect-by date is `collectByDate` on Hold Fulfilled. Both are computed by the handler
    (`assigned` in the .em), so every view reads the same date.
  - **Outgoing emails (overdue and pickup notices):** the decision is recorded first (Overdue
    Notice Sent / Pickup Notice Sent), then handed to the provider; the hand-off is driven from
    the recorded event and resumes after a restart until the provider accepts (an outbox — not a
    domain event). The Sent event carries what the notice was sent with — the address it went to
    and the content shown (names, tool, dates) — as facts of the notice; this is the one
    exception to "events don't carry copies of names", because those are what was actually sent.
    The loan or hold id is the hand-off key the provider's failure report quotes.
  - **Time-driven readers:** the two automations whose lists fill when a date passes (the
    overdue notice gateway, the pickup expirer) read their list every 5 minutes, at any hour.
    Event-driven readers act whenever their list changes.
  - **Neighbor Account Closed carries** `whileSuspended` (Bool, assigned): whether the account
    was suspended when it closed, decided once. Register Neighbor and Change Email read it to
    apply N9; they don't work it out from suspension history.
  - **Loan-ending events carry both keys:** Tool Returned and Tool Lost carry `loanId` and
    `toolId`, so views about tools or holds match on the tool directly.
  - **Queue order:** a tool's hold queue is the order in which Hold Placed was recorded;
    `placedAt` is for display only (timestamps can tie).
  - **Text:** leading/trailing whitespace (any Unicode whitespace) is trimmed; empty after
    trimming means absent.
  - **Types:** one vocabulary in both the docs' field tables and the .em field blocks — Text,
    Int, Bool, Date, Instant, `<Thing>Id` — because `em validate` compares the two. Whether a
    field is optional goes in the Required column or the notes, never in the type.
  - **Named values:** status values and refusal names are both kebab-case (`checked-out`,
    `set-aside`, `period-out-of-range`).
  - **Refusals:** a refusal records nothing and returns one reason: a stable name (e.g.
    `period-out-of-range`) plus one sentence, listed once under Alternate & Error Flows and used
    word for word in each rejection scenario. The name is the contract; the sentence is the text
    shown to the person. A name means the same condition in every slice (the sentence may be
    fitted to the action); different conditions get clearly different names.
  - **Invariants:** an INV ID belongs in a doc only if that slice's own command, event or view
    enforces it and a test in that slice can show it. Rules owned elsewhere are stated in prose
    and point to the owning slice's INV. Every rule scenario cites the INV it exercises.
  - **View fields in the .em:** every field of a view is declared on its first declaration; a
    field the first declaration's own events supply is plain, even if a later event replaces
    it (e.g. a neighbor's email); a field supplied only by an event the first declaration
    doesn't hear is bare `derived`; a field that copies an event field under a different name
    (e.g. `toolName` from Tool Added's `name`) is `derived from "<that event>"`, so one
    `em export --slice` carries the whole row. Each view doc states the queries it answers (what
    each takes and returns).
  - **Open dependencies stay visible:** a doc that depends on a question still open with Mike
    Key carries it as an unchecked item in its own Open Questions — one line naming the brief
    item — until he rules, so the readiness gate can't pass it early. Identity (brief 10 A1) is
    the common one.
  - **Hold Fulfilled carries** `holdId`, `toolId`, `neighborId`, `collectByDate`, `fulfilledAt`
    (ids, not names), so views that don't hear Hold Placed can match a set-aside to its tool and
    holder.
