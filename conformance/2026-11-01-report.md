## Findings

### 1. Record Tool Lost carries a route `toolId` the model does not declare, and refuses on it

- **Surface:** structural
- **Classification:** model gap
- **Slice:** record-tool-lost
- **Evidence:** `em diff` entry `field-added` / `command` / `Record Tool Lost` / field `toolId: ToolId`; `src/main/kotlin/com/toolshed/recordtoollost/RecordToolLost.kt:12-13`; `src/main/kotlin/com/toolshed/recordtoollost/RecordToolLostDecider.kt:23-26` (route toolId not equal to the loan's tool → `loan-not-found`, cited to INV-LOST-11); route `PUT /api/tools/{toolId}/loans/{loanId}/lost`; constitution Amendment 10 (tools live under `/api/tools/{toolId}`); code comment "lead ruling, record-tool-lost route" with no matching entry in `.event-modeling.md`.
- **Claim:** the model's command is `{ loanId }` and the doc's INV-LOST-11 says only "the loan must have been checked out"; the code's command is `{ loanId, toolId }` and adds a refusal when the route's tool is not the loan's tool. The behaviour follows Amendment 10's URL layout, but neither the `.em` nor the slice doc records the field or the rule.
- **Proposed red note:** `issue "conformance: code carries toolId from the route and refuses loan-not-found when it is not the loan's tool (Amendment 10 URL layout) — declare toolId on the command and extend INV-LOST-11, or drop the route check"` on command "Record Tool Lost" (slice "record-tool-lost")

### 2. Email Provider Failure Report (overdue) has no inbound transport and a fail-closed verifier

- **Surface:** structural
- **Classification:** real drift
- **Slice:** record-overdue-notice-failure
- **Evidence:** `src/main/kotlin/com/toolshed/recordoverduenoticefailure/OverdueNoticeFailureTranslation.kt` — `receive()` has no caller in `src/main` (grep); `src/main/kotlin/com/toolshed/axon/SharedPorts.kt:36-45` — the only `FailureReportVerifier` is `FailClosedFailureReportVerifier`, selected for provider `logging` (`application.yml` default); constitution Amendment 8: "A logging stub stands in until a provider is chosen."
- **Claim:** the model's translation "Email Provider Failure Report" is externally triggered and the doc says the provider "sends one final failure report" that the shed verifies and acts on. In the shipped app no request can reach the translation and any report that did would be rejected. The gap is deliberate under Amendment 8 but the model element carries no `divergence` annotation, so each conform run will re-report it.
- **Proposed red note:** rather than an `issue`, annotate the element so the deviation is ratified once: `translation Email Provider Failure Report divergence "No email provider selected (constitution Amendment 8): no inbound transport and the verifier fails closed until one is chosen"` (slice "record-overdue-notice-failure"). An `issue "conformance: …"` with the same text is the alternative if the intent is to track wiring the transport as open work.

### 4. Tool Catalog re-creates a retired or lost tool on a duplicate Tool Added

- **Surface:** spec
- **Classification:** real drift
- **Slice:** tool-catalog
- **Evidence:** `src/main/kotlin/com/toolshed/toolcatalog/ToolCatalogRepository.kt:56` (`computeIfAbsent` on add), `:118` and `:122` (`tools.remove` on retire and on lost, with no record of the drop). Contrast `src/main/kotlin/com/toolshed/toolinventory/ToolInventoryRepository.kt:37,49` (`dropped` set guards re-add). No test covers it: `ToolCatalogProjectionTest.kt:307` replays Tool Returned, not Tool Added.
- **Claim:** INV-TCAT-12 ("Applying the same event twice leaves the catalog as if it had been applied once") and INV-TCAT-8 ("A retired tool drops off the catalog at once") are not guaranteed: a Tool Added redelivered after Tool Retired or Tool Lost re-creates the catalog entry. Only reachable by an out-of-order duplicate delivery, not by an in-order token replay, so no observable defect today; the inventory projection guards the same case, the catalog does not.
- **Proposed red note:** none — the fix is code-side (a `dropped` set as in Tool Inventory, plus a test); ruling `locus: code` carries that.

## Uncertainties

- **internal** — 18 `doc-names-unfed-event` warnings from `em validate` — holds-to-fulfill (5), overdue-loans-to-notify (4), neighbors-to-flag (3), pickup-notices-to-send (3), pickups-to-expire (3) — each names an event the doc says the view reads but the view's `from` list omits. In every case the `.em` carries the edge as `loops-to "<View>"` on the event (`toolshed.em:196,246,322,348,374`), and the DSL reference says `loops-to` counts as the event being read. The code projections handle every one of those events. So the doc, the model and the code agree; what is unclear is whether the validator rule should honour `loops-to`, or whether the house style wants those events repeated in `from`. A tooling question for em, not a model finding.
- **structural** — processor assignment in the running app — overdue-loans-to-notify, send-overdue-notice — the slice `Configuration` objects register each projection and the outbox on a dedicated pooled-streaming processor for the test fixture (`OverdueLoansToNotifyConfiguration.kt:9-39`, `SendOverdueNoticeConfiguration.kt:33-45`); in the Spring app the `@Component`s are auto-detected and no explicit assignment was found, so whether the outbox's throw halts a dedicated processor or a shared one was not verified without running the app.
- **spec** — outbox restart semantics (INV-OVN-4, INV-PKN equivalent) — send-overdue-notice, send-pickup-notice — `OverdueNoticeOutbox.kt:23` says the token "carries across a restart", but `axon/TokenStoreConfiguration.kt:16` gives every processor an `InMemoryTokenStore` (deliberately, so views rebuild). A restart therefore replays the whole stream and re-hands every historical notice to the provider; duplicates are prevented only by the provider's one-email-per-key contract (Amendment 8, `EmailGateway.kt:17`). The doc's observable claim (hand-off resumes after restart until accepted) still holds; the KDoc is stale and whether whole-stream re-hand-off was intended for the outbox was not determined.
- **spec** — INV-MYL-12 "My Loans offers Return on every loan it lists" — my-loans — no enforcement site: neither the model's view fields nor `MyLoanRow` carry a `canReturn` flag (the row has `canExtend` only). The rule is realised by Return Tool refusing nothing for suspension, overdue or retirement (verified under return-tool), so nothing in this slice can be cited. Tests cited by coverage.json (`MyLoansProjectionTest.kt:26,191`) assert listing, not a flag.
- **spec** — Overdue Notice Sent applied after Overdue Notice Failed — my-loans — `MyLoansRepository.kt:71` overwrites `noticeSent` unconditionally; the doc defines only Failed-after-Sent, so a reordered redelivery would flip "undelivered" back to "sent". No doc scenario asserts either way.
- **spec** — concurrent same-email sign-ups — register-neighbor — enforcement site exists (`NeighborRegistryState.kt:71-80` DCB criteria plus `RegisterNeighborCommandHandler.kt:30` append on the same context) but no slice test exercises two concurrent sign-ups; the foundation test `axon/AppendDisciplineOverAxonServerTest.kt` may, not verified for this slice. Related: change-email and register-neighbor use two different ledger entities with overlapping type-only criteria (`EmailRegistryState` vs `NeighborRegistryState.kt:13,25`); that they form one effective boundary relies on Axon Server honouring type-only append conditions, not verified by running.
- **spec** — consistency boundary wider than the doc states — expire-hold — the doc says expiries are "decided one at a time per tool"; `ExpireHold.kt:15` and `ExpireState.kt:82-93` decide against one shed-wide `ExpireLedger` (`havingAnyTag`), serialising all expiries. Also: the expirer reads its list by calling the query handler directly (`PickupExpirerConfiguration.kt:24`) while the pickup gateway reads the repository (`SendPickupNoticeConfiguration.kt:62`); functionally equivalent in-process, noted only because the two automations differ.
